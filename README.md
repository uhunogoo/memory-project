# Book Memory

Перший етап локального пошуку по Markdown-книгах: структура книг, AST-парсинг, чанкінг, основна БД контенту та незалежна пошукова БД з гібридним пошуком. Написання підсумкової відповіді моделлю та вебінтерфейс належать наступному етапу.

## Запуск

Потрібні Node.js 24+ та [Vite+](https://viteplus.dev/guide/). Проєкт створено на основі шаблону Vite+ для TypeScript-бібліотек; CLI та бібліотека збираються через `vp pack`.

```bash
vp install
vp run build
vp run memory init
```

Тека `books/` спочатку порожня. Додайте власні книги, потім:

```bash
vp run memory index
vp run memory books
vp run memory search "як працює пам'ять" --mode lexical
vp run memory status
```

Без конфігурації моделей індексація тексту та BM25 працюють локально. `index` повідомить, що embeddings ще не налаштовано. Порожня бібліотека — нормальний стан.

```bash
vp run memory --help
vp run check
vp run test
```

## Структура книг

**Кожна тека першого рівня всередині `books/` — окрема книга.** Markdown шукається рекурсивно, розширення `.md` нечутливе до регістру. Файли безпосередньо в `books/` пропускаються з попередженням. Символічні посилання не підтримуються. Зображення й інші файли не індексуються; їхні посилання залишаються в оригінальному Markdown.

```text
books/
  Перша книга/
    book.md
  Друга книга/
    01-вступ.md
    частина-1/
      01-розділ.md
      02-розділ.md
    images/
      diagram.png
```

Назва книги за замовчуванням — назва її теки. Порядок файлів — природне сортування відносних шляхів: `2` перед `10`. Структура тек сама по собі не створює розділи: їх визначають Markdown-заголовки. Чанки не перетинають межі файлів.

За потреби додайте **`book.json` усередині теки конкретної книги**:

```json
{
  "title": "Назва книги для пошуку",
  "author": "Автор",
  "language": "uk",
  "files": ["01-вступ.md", "частина-1/02-розділ.md", "частина-1/01-розділ.md"]
}
```

Усі поля необов'язкові. Якщо `files` задано, це точний склад і порядок книги: решта Markdown-файлів виключається. Шляхи задаються відносно теки книги, з `/`; дублікати, вихід за межі теки, відсутні файли та невідомі поля спричиняють помилку. Некоректна книга перериває сканування до зміни текстового індексу, щоб помилка читання не виглядала як видалення джерел.

Назва окремого документа визначається YAML frontmatter `title`, першим H1 або назвою книги. Метадані не змінюють назву книги з теки/`book.json`. Перейменування теки книги або файлу змінює його ідентичність; після наступної індексації використовуйте актуальні ідентифікатори.

## Embeddings

Скопіюйте `memory.config.example.json` у `memory.config.json`, задайте модель, яка вже доступна у вашого провайдера. Проєкт не завантажує моделі автоматично. Для Ollama приклад містить шаблон `your-embedding-model`, який потрібно замінити.

```bash
vp run memory index
# Або окремо: спочатку контент і лексичний індекс, пізніше embeddings
vp run memory index --no-embed
vp run memory embed
vp run memory search "пояснення своїми словами" --mode hybrid
vp run memory search "пояснення своїми словами" --mode vector --json
```

Для іншого OpenAI-compatible сервісу приклад конфігурації:

```json
{
  "booksDir": "./books",
  "dataDir": "./.data",
  "chunking": { "targetTokens": 800, "overlapTokens": 100 },
  "embedding": {
    "provider": "openai-compatible",
    "baseUrl": "http://127.0.0.1:8080/v1",
    "model": "your-embedding-model",
    "apiKeyEnv": "EMBEDDING_API_KEY",
    "batchSize": 16,
    "timeoutMs": 60000,
    "retries": 2,
    "documentPrefix": "",
    "queryPrefix": ""
  }
}
```

`apiKeyEnv` можна прибрати, якщо сервер не потребує ключа. Ключ задається змінною середовища або в `.env` для `vp run memory`; конфігурація не приймає ключ безпосередньо. `.env`, особисті налаштування, книги та БД виключені з Git. HTTP-адаптери не зберігають ключі в БД та не виводять тіла помилок провайдера.

Шляхи `booksDir` і `dataDir` відносні до файлу конфігурації. Інший файл можна вибрати через `--config /path/to/config.json`. `baseUrl` — базова адреса: Ollama додає `/api/embed`, сумісний сервіс — `/embeddings`. Наявність лише chat endpoint не означає підтримку embeddings.

Опційне поле `dimensions` задає розмірність, якщо це підтримує модель/провайдер. Без нього розмірність визначається першою відповіддю й фіксується для профілю. `documentPrefix` і `queryPrefix` налаштовуються відповідно до вимог конкретної embedding-моделі, включно з потрібними пробілами. Обирайте модель із підтримкою мов ваших книг.

Мережеві запити йдуть тільки до налаштованих endpoint: туди передається текст чанків із назвою книги/розділу та пошукові запити. Генерації відповідей на цьому етапі немає. Ollama викликається з `truncate: false`: переповнення контексту дає явну помилку, а не непомітне обрізання тексту.

## Реранкер

Реранкер оцінює релевантність знайдених чанків до початкового запиту. Налаштований реранкер автоматично працює після `lexical`, `vector` та `hybrid` пошуку. Для наявних змінних достатньо задати в оточенні або `.env` для `vp run memory`:

```dotenv
COHERE_RERANK_URL=https://api.cohere.com/v2/rerank
COHERE_RERANK_MODEL=your-reranking-model
COHERE_RERANK_API_KEY=your-api-key
```

Підтримуються також нейтральні назви `RERANK_URL`, `RERANK_MODEL`, `RERANK_API_KEY`: кожна має пріоритет над відповідною `COHERE_RERANK_*`. URL — **повна адреса операції**, включно з `/v2/rerank`, `/v1/rerank` або іншим потрібним шляхом; застосунок нічого не дописує. Ключ необов'язковий для локальних серверів. Часткові або некоректні налаштування спричиняють явну помилку.

Використовується звичайний HTTP POST без SDK провайдера: `{ model, query, documents: string[], top_n }`, відповідь — `{ results: [{ index, relevance_score }] }`, авторизація — Bearer. Це поширений **Cohere-сумісний контракт**, а не стандарт для всіх API; його підтримують [Cohere](https://docs.cohere.com/v2/reference/rerank) та [сумісні сервери vLLM](https://docs.vllm.ai/en/latest/models/pooling_models/scoring/#cohere-rerank-api). Сервер має повертати оцінку від 0 до 1 для кожного переданого чанка. Щоб змінити сумісний сервіс або модель, змініть URL, модель і за потреби ключ; перебудовувати індекс не потрібно.

Опційний блок у `memory.config.json`:

```json
{
  "rerank": {
    "url": "http://127.0.0.1:8000/rerank",
    "model": "your-reranking-model",
    "candidateLimit": 40,
    "timeoutMs": 60000,
    "retries": 2
  }
}
```

`url` та `model` у JSON мають пріоритет над оточенням; пропущені поля беруться з нього. `apiKeyEnv` дозволяє вибрати іншу змінну з ключем. `"rerank": false` вимикає реранкер, навіть якщо змінні задані. `loadConfig()` читає лише оточення процесу та JSON; `.env` завантажує команда `memory`. Збірка й тести не завантажують `.env`.

```bash
vp run memory search "як працює пам'ять" --limit 5 --json
vp run memory search "як працює пам'ять" --no-rerank
# Лише локальний BM25, без звернення до моделей:
vp run memory search "пам'ять" --mode lexical --no-rerank
```

Алгоритм спирається на [реалізацію QMD](https://github.com/tobi/qmd/blob/main/src/store.ts): після RRF та усунення перекриттів беремо до 40 кандидатів, оцінюємо моделлю, змішуємо оцінки й лише тоді застосовуємо `--limit`. `candidateLimit` можна змінити в межах 1–100; якщо `--limit` більший, пул зростає до нього. Передаємо вже готові `embeddingText` чанків із назвою книги та заголовками; embedding-префікси до реранкера не додаються. Фільтр книги застосовується до відбору кандидатів. Пошук і реранкінг не читають Content DB.

Фінальна оцінка: `w / rank + (1 - w) * relevance_score`, де ранг починається з 1; `w` дорівнює 0.75 для рангів 1–3, 0.60 для 4–10 та 0.40 далі. Ця консервативна формула завжди зберігає перший результат retrieval на першому місці. У JSON `score` містить змішану оцінку, `rrfScore` — початкову, `rerankScore` — оцінку моделі. Це не ймовірності правильності відповіді. Без успішного реранкінгу `score` залишається RRF, додаткові поля відсутні.

Таймаут, мережева помилка або некоректна відповідь залишають початковий порядок і оцінки пулу кандидатів із попередженням у `warnings`. Тимчасові HTTP/мережеві помилки повторюються до `retries` разів. Реранкер викликається тільки під час пошуку з непорожнім списком кандидатів; оцінки не кешуються. Через API бібліотеки його можна вимкнути опцією `rerank: false` або замінити реалізацію через `dependencies.reranker` із контрактом `RerankProvider`.

## Контент і пошуковий індекс

| Файл                   | Призначення                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.data/content.sqlite` | Основне джерело: книги, оригінальні Markdown-файли поточної індексованої версії, розділи, чанки, результат останнього запуску та блокування індексатора |
| `.data/vectors.sqlite` | Відновлюваний пошуковий індекс: копії чанків із текстом, метаданими та координатами, FTS5, профілі моделей й embeddings                                 |

```text
Markdown → парсинг і чанкування → ContentRepository
                                       │
                                  індексація
                                       ↓
                                SearchRepository
                          текст + FTS5 + embeddings
                                       ↑
                         lexical / vector / hybrid
```

Увесь пошук виконується через `SearchRepository`: лексичний і векторний пошук, фільтри, RRF та усунення перекриттів працюють над даними пошукової БД. Результат уже містить текст і координати фрагмента; пошуковий запит не читає Content DB. Команди читання книг, розділів, чанків і повних документів використовують `ContentRepository`.

Пошукове сховище реалізоване безпосередньо в `src/storage/search.ts`: SQLite FTS5 і sqlite-vec, точний cosine-пошук, не ANN. Окремого контракту для альтернативних рушіїв немає. Локальні операції сховищ, `BookLibrary.status()` і `close()` синхронні; `index()`, `embed()` і `search()` асинхронні через файлові та HTTP-операції.

Публічний API пакета: `BookLibrary`, `initializeLibrary`, `loadConfig`, `createRerankProvider` і типи конфігурації, опцій та результатів, включно з `RerankProvider`. Парсер, embedding-провайдер і конкретні сховища є внутрішніми модулями. Старі назви `VectorRepository`, `SqliteVectorRepository` і параметр `dependencies.vectors` видалено.

Процес індексації збережено:

- `index` читає джерела, оновлює Content DB і переносить підготовлені чанки в Search DB. За наявності провайдера генерує відсутні embeddings.
- `index --no-embed` також оновлює пошукові тексти, метадані й FTS5, прибирає видалені записи та перевикористовує кешовані embeddings, але не викликає модель.
- `embed` відновлює пошукові записи зі збережених чанків і генерує відсутні embeddings без читання вихідних Markdown-файлів. Цією командою можна відбудувати Search DB із Content DB.

Лексичний індекс заповнюється незалежно від embeddings, тому працює без провайдера. Індексація пропускає незмінені файли, враховує версію чанкінгу/параметри та назву книги. Пошуковий payload оновлюється й тоді, коли вектор можна перевикористати. Embeddings кешуються за однаковим модельним входом у межах профілю. Зміна провайдера, endpoint, моделі, розмірності чи префіксів створює інший профіль. Якщо сервер замінив ваги моделі під тією самою назвою, використайте версіоновану назву/endpoint або перебудуйте пошукову БД: автоматично розпізнати таку заміну неможливо.

Дві БД не мають спільної транзакції. Черги завдань немає: кожен `index` або `embed` звіряє збережені чанки з пошуковим сховищем. Спочатку оновлюються payload і FTS5, потім перевикористовуються кешовані embeddings та, якщо дозволено, генеруються відсутні. Наприкінці видаляються зайві записи. Старі ID очищаються після перевикористання кешу, щоб перейменування файлу не вимагало повторного виклику моделі. Після збою наступний запуск повторює той самий алгоритм.

Пошуковий адаптер транзакційно записує payload, FTS5 і вектори. Одночасно записувати може один індексатор; блокування охоплює також HTTP-запити й відновлюється за PID після завершення аварійного процесу на тому самому хості. Пошук використовує поточний стан Search DB. Історія запусків не накопичується: зберігається лише останній результат.

Поточні БД v2 автоматично переходять на v3 без втрати контенту й embeddings: видаляються `vector_jobs`, нечитані метадані профілів і старі записи історії запусків. Підтримку v1 прибрано; така БД відхиляється без автоматичного стирання даних. Для v1 спочатку скористайтеся попередньою версією проєкту для переходу на v2 або окремо збережіть дані й перебудуйте індекс. Назва `vectors.sqlite` зберігається.

`status` показує `vectors.pendingEmbeddings` — кількість чанків Content DB без актуального вектора поточного профілю. Значення `null` означає, що провайдер не налаштований або сховище недоступне; це не нуль відсутніх embeddings. Поля `pendingVectorJobs` і `failedVectorJobs` видалено. Помилки останнього запуску доступні в `lastRun.details`, а незавершені embeddings визначаються за даними, без історичних статусів завдань. Якщо пошукова БД відсутня, `embed` відбудує її з контенту за наявності провайдера; без провайдера запустіть `index --no-embed`.

SQLite використовує WAL; для резервування живих баз потрібен коректний SQLite backup, або закрийте всі процеси перед копіюванням файлів.

## Фрагменти та координати

Парсер використовує Markdown AST (CommonMark + GFM + YAML frontmatter), а не регулярні вирази для визначення заголовків. Підтримуються вкладені розділи, повторні заголовки, списки, таблиці, цитати й блоки коду.

Чанк містить дослівний `markdown` та окремі `text`/`embeddingText`. `headingPath`, `anchor`, `relativePath` і `documentId` дозволяють відкрити відповідне місце в майбутньому читачі. Anchors генеруються за правилами GitHub із розв'язанням дублікатів; для преамбули є `top`. Читач наступного етапу має використовувати збережені anchors, а не обчислювати інші.

- `startOffset`/`endOffset` — позиції UTF-16 у збереженому рядку Markdown, кінець виключний: `markdown.slice(startOffset, endOffset)` точно відтворює фрагмент.
- `startLine`/`endLine` — номери рядків від 1, обидва включні. Оригінальні CRLF і Unicode зберігаються.
- Розмір чанка — оцінка UTF-8 байтів / 3, **не точний підрахунок токенів моделі**. Бюджет враховує назву книги та шлях заголовків; додаткові префікси провайдера також потребують запасу.
- Перекриття обмежується всередині розділу. Надмірно великі таблиці, списки й блоки коду можуть ділитися по рядках/словах із точними координатами; окремий фрагмент у такому випадку не обов'язково є самодостатнім Markdown-блоком.

```bash
vp run memory books
vp run memory sections --book BOOK_ID
vp run memory chunks --book BOOK_ID
vp run memory get CHUNK_ID
vp run memory document DOCUMENT_ID
vp run memory search "запит" --book BOOK_ID --limit 5 --json
```

BM25 працює по чанках із підсиленням назви книги та заголовків. `unicode61` підтримує Unicode, але не лематизує українські слова: різні словоформи можуть не збігатися лексично. Семантична гілка залежить від якості обраної моделі. RRF об'єднує ранги двох списків (`k=60`); оцінки не є ймовірністю правильності. Значне перекриття результатів одного документа прибирається.

У режимі `hybrid` недоступна модель дає текстові результати з явним попередженням; режим `vector` повідомляє помилку провайдера. Неповний семантичний індекс також позначається попередженням. Пошук найближчих векторів не гарантує, що книга містить відповідь — генерації висновків тут немає.

CLI завершується з кодом `0` при успіху, `1` при помилці команди та `2`, якщо текст проіндексований, але векторний етап частково не завершений. Деталі доступні через `status`; `embed` генерує відсутні embeddings.

## Перевірки та наступний етап

Zod перевіряє зовнішні дані одразу після JSON/YAML-декодування: конфігурацію, `book.json`, frontmatter та відповіді embedding/rerank API. Схеми визначають об'єкти, поля, типи й масиви без автоматичного приведення значень. Конфігурація та `book.json` відхиляють невідомі поля; frontmatter й API-відповіді допускають додаткові метадані. Frontmatter має бути об'єктом з необов'язковим рядковим `title`; порожній YAML та YAML `null` / `~` трактуються як відсутність метаданих. Помилки структурної перевірки не виводять значення зовнішніх даних.

Структурні перевірки залишаються на публічних входах `BookLibrary`, `initializeLibrary()`, `index()` і `search()`, а також для JSON/YAML та HTTP-відповідей. Внутрішні виклики парсера й передавання текстів провайдеру використовують TypeScript-типи без повторної перевірки структури. CLI використовує `parseArgs` для прапорців і спільну схему режимів пошуку. Схеми розташовані поруч із кодом, який їх використовує.

Батчування виконує індексатор. Однакові входи групуються за хешем для всього запуску; придатний кеш переноситься до HTTP-запитів. Кожен відсутній унікальний вхід генерується один раз. Провайдер обробляє один переданий батч.

Бізнес-правила залишаються у TypeScript: defaults, числові межі й залежність overlap від розміру чанка, перевірки порожнього тексту, URL та API-ключів, правила шляхів і складу книги, існування файлів, відповідність кількості та порядку embeddings запиту, ненульовість і розмірність векторів, індексація й синхронізація БД. Завантаження конфігурації та створення провайдера використовують одну функцію перевірки значень конфігурації. У схемах немає цих правил через `refine`, `superRefine`, defaults або перетворення. Записи власної БД не проходять повторну Zod-валідацію. Версію парсера піднято для одноразової перевірки frontmatter вже індексованих книг; незмінений вхід моделі дозволяє повторно використати embeddings.

Тести використовують тимчасові каталоги, власні невеликі тексти, реальні обидві SQLite-бази й контрольовані відповіді провайдерів. Книги користувача не змінюються. Перевіряються координати, Unicode, порядок файлів, конфігурація, API-контракти, оновлення/видалення, профілі моделей та відновлення після збоїв. Зовнішні embedding/rerank-сервіси для тестів не потрібні.

Наступний етап: читач із переходами в розділи, інтерфейс пошуку, розширення запитів та окремий провайдер генерації відповідей із посиланнями на дослівні фрагменти.

Архітектурний орієнтир — [QMD](https://github.com/tobi/qmd): SQLite FTS5, sqlite-vec, природні межі чанків, хешування й RRF. У цьому проєкті реалізація власна: книга складається з файлів, обидва пошуки працюють по чанках, сховища розділені, inference відбувається через HTTP-провайдери. Технічні джерела: [Vite+ Pack](https://viteplus.dev/guide/pack), [sqlite-vec для Node.js](https://alexgarcia.xyz/sqlite-vec/js.html), [Ollama Embed API](https://docs.ollama.com/api/embed).
