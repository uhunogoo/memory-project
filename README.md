# Book Memory

Перший етап локального пошуку по Markdown-книгах: структура книг, AST-парсинг, чанкінг, незалежні текстова й векторна БД, інкрементальна індексація та базовий гібридний пошук. Написання підсумкової відповіді моделлю та вебінтерфейс належать наступному етапу.

## Запуск

Потрібні Node.js 24+ та [Vite+](https://viteplus.dev/guide/). Проєкт створено на основі шаблону Vite+ для TypeScript-бібліотек; CLI та бібліотека збираються через `vp pack`.

```bash
vp install
vp run build
vp run memory init
```

Тека `books/` спочатку порожня. Додайте власні книги, потім:

```bash
vp run memory index
vp run memory books
vp run memory search "як працює пам'ять" --mode lexical
vp run memory status
```

Без конфігурації індексація тексту та BM25 працюють локально без моделі. `index` повідомить, що embeddings ще не налаштовано. Порожня бібліотека — нормальний стан.

```bash
vp run memory --help
vp run check
vp run test
```

## Структура книг

**Кожна тека першого рівня всередині `books/` — окрема книга.** Markdown шукається рекурсивно, розширення `.md` нечутливе до регістру. Файли безпосередньо в `books/` пропускаються з попередженням. Символічні посилання не підтримуються. Зображення й інші файли не індексуються; їхні посилання залишаються в оригінальному Markdown.

```text
books/
  Перша книга/
    book.md
  Друга книга/
    01-вступ.md
    частина-1/
      01-розділ.md
      02-розділ.md
    images/
      diagram.png
```

Назва книги за замовчуванням — назва її теки. Порядок файлів — природне сортування відносних шляхів: `2` перед `10`. Структура тек сама по собі не створює розділи: їх визначають Markdown-заголовки. Чанки не перетинають межі файлів.

За потреби додайте **`book.json` усередині теки конкретної книги**:

```json
{
  "title": "Назва книги для пошуку",
  "author": "Автор",
  "language": "uk",
  "files": ["01-вступ.md", "частина-1/02-розділ.md", "частина-1/01-розділ.md"]
}
```

Усі поля необов'язкові. Якщо `files` задано, це точний склад і порядок книги: решта Markdown-файлів виключається. Шляхи задаються відносно теки книги, з `/`; дублікати, вихід за межі теки, відсутні файли та невідомі поля спричиняють помилку. Некоректна книга перериває сканування до зміни текстового індексу, щоб помилка читання не виглядала як видалення джерел.

Назва окремого документа визначається YAML frontmatter `title`, першим H1 або назвою книги. Метадані не змінюють назву книги з теки/`book.json`. Перейменування теки книги або файлу змінює його ідентичність; після наступної індексації використовуйте актуальні ідентифікатори.

## Embeddings

Скопіюйте `memory.config.example.json` у `memory.config.json`, задайте модель, яка вже доступна у вашого провайдера. Проєкт не завантажує моделі автоматично. Для Ollama приклад містить шаблон `your-embedding-model`, який потрібно замінити.

```bash
vp run memory index
# Або окремо: спочатку текст, пізніше embeddings
vp run memory index --no-embed
vp run memory embed
vp run memory search "пояснення своїми словами" --mode hybrid
vp run memory search "пояснення своїми словами" --mode vector --json
```

Для іншого OpenAI-compatible сервісу приклад конфігурації:

```json
{
  "booksDir": "./books",
  "dataDir": "./.data",
  "chunking": { "targetTokens": 800, "overlapTokens": 100 },
  "embedding": {
    "provider": "openai-compatible",
    "baseUrl": "http://127.0.0.1:8080/v1",
    "model": "your-embedding-model",
    "apiKeyEnv": "EMBEDDING_API_KEY",
    "batchSize": 16,
    "timeoutMs": 60000,
    "retries": 2,
    "documentPrefix": "",
    "queryPrefix": ""
  }
}
```

`apiKeyEnv` можна прибрати, якщо сервер не потребує ключа. Ключ задається змінною середовища або в `.env` для `vp run memory`; конфігурація не приймає ключ безпосередньо. `.env`, особисті налаштування, книги та БД виключені з Git. HTTP-адаптери не зберігають ключі в БД та не виводять тіла помилок провайдера.

Шляхи `booksDir` і `dataDir` відносні до файлу конфігурації. Інший файл можна вибрати через `--config /path/to/config.json`. `baseUrl` — базова адреса: Ollama додає `/api/embed`, сумісний сервіс — `/embeddings`. Наявність лише chat endpoint не означає підтримку embeddings.

Опційне поле `dimensions` задає розмірність, якщо це підтримує модель/провайдер. Без нього розмірність визначається першою відповіддю й фіксується для профілю. `documentPrefix` і `queryPrefix` налаштовуються відповідно до вимог конкретної embedding-моделі, включно з потрібними пробілами. Обирайте модель із підтримкою мов ваших книг.

Мережеві запити йдуть тільки до налаштованого endpoint: туди передається текст чанків із назвою книги/розділу та пошукові запити. Генерації відповідей на цьому етапі немає. Ollama викликається з `truncate: false`: переповнення контексту дає явну помилку, а не непомітне обрізання тексту.

## Що зберігається

| Файл                   | Призначення                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `.data/content.sqlite` | Книги, оригінальні Markdown-файли поточної індексованої версії, розділи, чанки, FTS5, журнал запусків і черга векторних завдань |
| `.data/vectors.sqlite` | Профілі моделей, вектори, ідентифікатори чанків і хеші вхідного тексту                                                          |

`ContentRepository` та `VectorRepository` відокремлюють отримання тексту від векторного пошуку. Основне джерело даних — `content.sqlite`; векторну БД можна відбудувати командою `embed` із текстової БД, навіть без доступу до вихідних файлів. SQLite використовує WAL; для резервування живих баз потрібен коректний SQLite backup, або закрийте всі процеси перед копіюванням файлів.

Індексація пропускає незмінені файли, враховує версію чанкінгу/параметри та назву книги, оновлює FTS5 в одній транзакції з текстом. Вектори перевикористовуються для однакового модельного входу в межах профілю. Зміна провайдера, endpoint, моделі, розмірності чи префіксів створює інший профіль. Якщо сервер замінив ваги моделі під тією самою назвою, використайте версіоновану назву/endpoint або перебудуйте векторну БД: автоматично розпізнати таку заміну неможливо.

Дві БД не мають спільної транзакції. Завдання на оновлення/видалення записуються в основну БД; повторне виконання безпечне. Після перерваного запису наступний запуск звіряє індекси, прибирає осиротілі вектори та відновлює відсутні. Одночасно записувати може один індексатор; блокування після завершеного аварійного процесу відновлюється за PID на тому самому хості.

Векторний пошук перевіряє профіль і актуальний хеш **до** відбору найкращих результатів. Застарілі embeddings та інші книги не витісняють релевантні результати. Для кількох книг використовується точний cosine-пошук по придатних векторах; це не ANN-індекс для мільйонів чанків.

## Фрагменти та координати

Парсер використовує Markdown AST (CommonMark + GFM + YAML frontmatter), а не регулярні вирази для визначення заголовків. Підтримуються вкладені розділи, повторні заголовки, списки, таблиці, цитати й блоки коду.

Чанк містить дослівний `markdown` та окремі `text`/`embeddingText`. `headingPath`, `anchor`, `relativePath` і `documentId` дозволяють відкрити відповідне місце в майбутньому читачі. Anchors генеруються за правилами GitHub із розв'язанням дублікатів; для преамбули є `top`. Читач наступного етапу має використовувати збережені anchors, а не обчислювати інші.

- `startOffset`/`endOffset` — позиції UTF-16 у збереженому рядку Markdown, кінець виключний: `markdown.slice(startOffset, endOffset)` точно відтворює фрагмент.
- `startLine`/`endLine` — номери рядків від 1, обидва включні. Оригінальні CRLF і Unicode зберігаються.
- Розмір чанка — оцінка UTF-8 байтів / 3, **не точний підрахунок токенів моделі**. Бюджет враховує назву книги та шлях заголовків; додаткові префікси провайдера також потребують запасу.
- Перекриття обмежується всередині розділу. Надмірно великі таблиці, списки й блоки коду можуть ділитися по рядках/словах із точними координатами; окремий фрагмент у такому випадку не обов'язково є самодостатнім Markdown-блоком.

```bash
vp run memory books
vp run memory sections --book BOOK_ID
vp run memory chunks --book BOOK_ID
vp run memory get CHUNK_ID
vp run memory document DOCUMENT_ID
vp run memory search "запит" --book BOOK_ID --limit 5 --json
```

BM25 працює по чанках із підсиленням назви книги та заголовків. `unicode61` підтримує Unicode, але не лематизує українські слова: різні словоформи можуть не збігатися лексично. Семантична гілка залежить від якості обраної моделі. RRF об'єднує ранги двох списків (`k=60`); оцінки не є ймовірністю правильності. Значне перекриття результатів одного документа прибирається.

У режимі `hybrid` недоступна модель дає текстові результати з явним попередженням; режим `vector` повідомляє помилку провайдера. Неповний семантичний індекс також позначається попередженням. Пошук найближчих векторів не гарантує, що книга містить відповідь — генерації висновків тут немає.

CLI завершується з кодом `0` при успіху, `1` при помилці команди та `2`, якщо текст проіндексований, але векторний етап частково не завершений. Деталі доступні через `status`; `embed` повторює незавершені завдання.

## Перевірки та наступний етап

Zod перевіряє зовнішні дані одразу після JSON/YAML-декодування: конфігурацію, `book.json`, frontmatter та відповіді embedding API. Схеми визначають об'єкти, поля, типи й масиви без автоматичного приведення значень. Конфігурація та `book.json` відхиляють невідомі поля; frontmatter й API-відповіді допускають додаткові метадані. Frontmatter має бути об'єктом з необов'язковим рядковим `title`; порожній YAML та YAML `null` / `~` трактуються як відсутність метаданих. Помилки структурної перевірки не виводять значення зовнішніх даних.

Структурна перевірка також працює на публічних входах `search()`, `createEmbeddingProvider()`, `embed()` і `parseMarkdown()`. CLI використовує `parseArgs` для типів прапорців і Zod для допустимих команд та режимів; перетворення текстового `--limit` на число виконується явно у CLI. Режими пошуку мають спільну схему для CLI та бібліотеки. Файлова й готова конфігурації embeddings та параметри чанків використовують спільні визначення полів; відповідні TypeScript-типи виводяться зі схем. Програмні об'єкти допускають додаткові поля, які відкидаються з результату структурної перевірки.

`BookLibrary` та `initializeLibrary()` перевіряють структуру готового `AppConfig` перед створенням сховищ або директорій. `index()` перевіряє об'єкт параметрів і тип `embed` перед отриманням блокування та записами в БД: рядок `"false"` не приймається як boolean. Типи `AppConfig` та `IndexOptions` виводяться зі схем; шляхи, chunking та embedding використовують спільні визначення з файловою конфігурацією.

Бізнес-правила залишаються у TypeScript: defaults, числові межі й залежність overlap від розміру чанка, перевірки порожнього тексту, URL та API-ключів, правила шляхів і складу книги, існування файлів, відповідність кількості та порядку embeddings запиту, ненульовість і розмірність векторів, індексація й синхронізація БД. Файловий і програмний входи провайдера використовують одну функцію перевірки значень конфігурації. У схемах немає цих правил через `refine`, `superRefine`, defaults або перетворення. Записи власної БД не проходять повторну Zod-валідацію. Версію парсера піднято для одноразової перевірки frontmatter вже індексованих книг; незмінений вхід моделі дозволяє повторно використати embeddings.

Тести використовують тимчасові каталоги, власні невеликі тексти, реальні обидві SQLite-бази й контрольовані відповіді провайдерів. Книги користувача не змінюються. Перевіряються координати, Unicode, порядок файлів, конфігурація, API-контракти, оновлення/видалення, профілі моделей та відновлення після збоїв. Зовнішній embedding-сервіс для тестів не потрібен.

Наступний етап: читач із переходами в розділи, інтерфейс пошуку та окремий провайдер генерації відповідей із посиланнями на дослівні фрагменти. Reranking і розширення запитів поки не реалізовані.

Архітектурний орієнтир — [QMD](https://github.com/tobi/qmd): SQLite FTS5, sqlite-vec, природні межі чанків, хешування й RRF. У цьому проєкті реалізація власна: книга складається з файлів, обидва пошуки працюють по чанках, сховища розділені, inference відбувається через HTTP-провайдери. Технічні джерела: [Vite+ Pack](https://viteplus.dev/guide/pack), [sqlite-vec для Node.js](https://alexgarcia.xyz/sqlite-vec/js.html), [Ollama Embed API](https://docs.ollama.com/api/embed).
